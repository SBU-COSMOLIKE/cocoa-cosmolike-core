# 14. A second source inspection: integrating the calculation into CosmoLike

> **Archive status.** This source study records design proposals and validation requirements, not completed features. Read the [maintained implementation status](../threepcf.md) first. Both the mean and its covariance belong in `cosmolike/3pcf/`; earlier destination proposals using `fastnc/` or `covariances/` are superseded.

The C implementation remains feasible, with CPU OpenMP and SIMD as the first execution design. The additional source inspection identifies several boundaries that require explicit work: intrinsic-alignment amplitudes do not have identical conventions, the existing interface owns one mutable cosmology, power-spectrum readers implement different redshift prescriptions, and the core covariance interfaces describe two-point observables. These are concrete integration tasks. None requires CUDA, but none is resolved merely by translating an upstream array expression into C.

This chapter separates **confirmed source behavior** from **proposed tests**. It reads core HEAD `0c0cf3838852396933c7f49550e35917dad0537c`, the project bindings, and the upstream revisions recorded in Chapter 11. The working tree contains existing modifications in scale-cut code, notebook utilities, and tests; those were left untouched. No scientific calculation, import, compilation, or timing experiment was performed. The thread allocation behind the roughly 40-second example is unknown, so it supplies no measured serial fraction or ten-core scaling factor.

## 1. Match the physical parameters before sharing IA functions

**Confirmed:** CosmoLike's `set_nuisance_IA` writes the normalization $`c=0.01389`$ and, for redshift evolution, the pivot $`z_p=0.62`$. The pinned fastnc IA expression uses $`c=0.0134`$, while the Y6 training values supply $`z_p=0.3`$. The difference is about 3.7% in the normalization constant alone. This is a convention difference, not evidence that either number is a coding error. Passing identical numerical `A1` and `A2` values to the two interfaces does not describe identical physical alignment amplitudes. [Core setter](../../../../../cosmolike/generic_interface.cpp); [core pivot](../../../../../cosmolike/generic_interface.cpp); [fastnc coefficients](https://github.com/git-sunao/fastnc/blob/7b2336ce37a909bed51f07f32a2a4f096e71b6ce/fastnc/ia_bispectra.py#L597-L613); [Y6 values](https://github.com/rchgomes/desy6-3pcf/blob/fd59fe4fee694d359453d5f573d6a4a55a47a812/config/emulator/values-training.ini#L20-L26).

For a power-law amplitude, write its redshift dependence as $`A c[(1+z)/(1+z_p)]^\eta`$, leaving common density and growth factors outside. Matching that expression between interfaces requires

```math
A_{\rm core}=A_{\rm upstream}\,
\frac{c_{\rm upstream}}{c_{\rm core}}
\left(\frac{1+z_{p,\rm core}}{1+z_{p,\rm upstream}}\right)^\eta .
```

This applies separately to the two amplitudes with their respective exponents, provided the remaining physical conventions match. At nonzero exponent the pivot conversion also changes the derivative with respect to that exponent. A Gaussian prior on one amplitude coordinate cannot be copied unchanged to a different coordinate. One can instead retain the upstream parameters as the public parameters and perform the conversion internally. If Fisher results are transformed between coordinates, the same Jacobian must transform the derivatives and prior precision.

There are two further sign and factor conventions. `IA_A1_Z1` returns a positive amplitude for positive `A1`; its callers apply the negative alignment sign. `IA_A2_Z1` omits a factor of five that its callers insert. Fastnc's coefficients already include the negative sign in $`C_1`$ and the five in $`C_2`$. Thus a three-point routine calling the existing amplitude functions needs an explicit mapping, not another copy of the two-point integrand's prefactors. A future test should compare physical $`C_1(z)`$, $`C_2(z)`$, and $`C_{1\delta}(z)`$ on a redshift grid before comparing projected spectra. [Core amplitude definitions](../../../../../cosmolike/IA.c).

## 2. The power provider is reusable; its physics is not interchangeable

**Confirmed:** `Pdelta` selects the externally installed linear or nonlinear power table. The run-mode name `Halofit` does not make the C reader calculate Halofit internally. The project can install CAMB nonlinear power or a EuclidEmulator2-based result. The nonlinear reader also multiplies by a baryonic power ratio when that option is active. Calling it from a translated bispectrum routine therefore imports the host's particular power prescription and baryon choice. [Dispatch](../../../../../cosmolike/cosmo3D.c); [reader](../../../../../cosmolike/cosmo3D.c); provider paths (inspected host file `likelihood/_cosmolike_prototype_base.py`, line 753).

The upstream nonlinear IA reader, by contrast, evaluates $`P_{\rm nl}(k,0)D(z)^2`$. Its default IA calculation uses this reader, rather than the linear alternative. Replacing it with the host's full $`P_{\rm nl}(k,z)`$ changes the redshift dependence of the model. Chapter 8 identifies the cache consequence; the integration consequence is that the C interface needs a named power prescription. Reference reproduction should preserve the chosen upstream prescription; a full-redshift alternative should have its own physics comparison and Fisher derivatives. [Upstream nonlinear evolution](https://github.com/git-sunao/fastnc/blob/7b2336ce37a909bed51f07f32a2a4f096e71b6ce/fastnc/ia_bispectra.py#L106-L129); [default selection](https://github.com/git-sunao/fastnc/blob/7b2336ce37a909bed51f07f32a2a4f096e71b6ce/fastnc/ia_bispectra.py#L597-L623).

Growth also crosses a nontrivial boundary. Fastnc receives $`D(z)`$. CosmoLike's setter receives $`G(z)=D(z)/a`$, and `growfac` returns $`G(z)a/G(0)`$. Copying the fastnc array into `set_growth` would introduce an unwanted factor of $`a`$. The project derives its growth from the total-matter linear spectrum at a specified physical wavenumber. Massive neutrinos make growth depend on scale, so agreement of a scalar growth array is a modeling condition to record. [Growth setter](../../../../../cosmolike/generic_interface.cpp); [normalized reader](../../../../../cosmolike/cosmo3D.c); project growth construction (inspected host file `likelihood/_cosmolike_prototype_base.py`, line 835).

Fastnc also renormalizes the supplied linear spectrum in place to its requested $`\sigma_8`$, using its own integral. CosmoLike's power setters install their supplied values without that normalization step. The comparison record should include the actual arrays after preparation, not only the original CAMB output. A translated routine should not modify the host's shared power table. Reproducing this normalization, or demonstrating it is negligible at the agreed tolerance before removing it, is separate from optimizing interpolation. [Upstream normalization](https://github.com/git-sunao/fastnc/blob/7b2336ce37a909bed51f07f32a2a4f096e71b6ce/fastnc/ia_bispectra.py#L38-L77).

Two additional inputs need explicit treatment. The core cosmology setter deliberately receives only matter and baryon densities, Hubble rate, and neutrino density; it expects external tables to carry the remaining cosmological dependence. BiHalofit's upstream interface also takes $`n_s`$, $`\sigma_8`$, and dark-energy parameters. Those cannot be assumed to be valid fields in the existing core struct. The upstream wrapper fixes `wa` and `fnu0` to zero, while externally supplied power can still contain neutrino effects. Conversely, the core distinguishes total matter from cold matter plus baryons for halo quantities. A port must specify which field enters every bispectrum term; substituting the cold-matter spectrum merely because halo functions use it would change the calculation. [Core setter](../../../../../cosmolike/generic_interface.cpp); [upstream parameter dictionary](https://github.com/git-sunao/fastnc/blob/7b2336ce37a909bed51f07f32a2a4f096e71b6ce/fastnc/bispectrum.py#L1161-L1184); [cold-matter reader](../../../../../cosmolike/cosmo3D.c).

Baryonic corrections require the same discipline. A ratio for the power spectrum is not, by itself, a calibrated ratio for the bispectrum. Applying a separate upstream bispectrum correction to power that already contains feedback can also count a modification twice. Record the input power's status and the exact correction applied to each statistic before attempting a joint forecast.

## 3. Unit and interpolation checks belong at the interface

Let $`L_0=2997.92458\,{\rm Mpc}/h`$. The existing core converts wavenumber, distance, power, and a dimensionful bispectrum according to

```math
k_{\rm core}=L_0 k_{h/{\rm Mpc}},\qquad
\chi_{\rm core}=\chi_{{\rm Mpc}/h}/L_0,\qquad
P_{\rm core}=P_{({\rm Mpc}/h)^3}/L_0^3,\qquad
B_{\rm core}=B_{({\rm Mpc}/h)^6}/L_0^6.
```

The last relation follows from the bispectrum's volume-squared units; it is a requirement for the proposed interface, not an existing bispectrum setter. A useful future test checks that $`k^3P/(2\pi^2)`$ is invariant under conversion and that the projected statistic is dimensionless. The Python provider begins with physical Mpc units and converts by powers of $`h`$ before the core conversion. Keeping that distinction explicit prevents missing or duplicating $`h`$ factors in derivatives. [Core unit definitions](../../../../../cosmolike/cosmo3D.c).

The core power setters require a uniform $`\log_{10}k`$ grid and supported piecewise-uniform redshift grids. Their readers interpolate $`\ln P`$ bilinearly and extrapolate from the nearest edge bracket; they do not clamp the value to the boundary. Fastnc uses cubic splines in log power, while the Y6 adapter first resamples its nonlinear input with `np.interp`, which clamps outside its source range. These are distinct numerical operations. The adapter should check coverage, record any regridding, and compare both values and parameter derivatives. Once those choices are fixed, shared brackets and batched `p_lin_at_a` reads provide a concrete acceleration opportunity. [Core reader arithmetic](../../../../../cosmolike/cosmo3D.c); [Y6 resampling](https://github.com/rchgomes/desy6-3pcf/blob/fd59fe4fee694d359453d5f573d6a4a55a47a812/desy6_3pcf/fastnc_backend.py#L221-L225).

## 4. One initialized model can have many workers

**Confirmed:** `cosmology`, `nuisance`, `redshift`, the FAST-PT tables, and other model objects are globals. `initial_setup` resets structs, frees supplied cosmology tables, resets baryons and run-mode dispatch, and clears table-origin flags. It does not create an independent instance for every caller. A second concurrent Python model sharing these globals could replace arrays still being read by the first. The initial design should use one installed model per process and many OpenMP workers within its calculation. Different Fisher perturbations can use separate processes; independently owned contexts would require additional implementation. [Global definitions](../../../../../cosmolike/structs.c); [setup](../../../../../cosmolike/generic_interface.cpp).

The CFASTPT functions demonstrate why inner parallelism and concurrent entry are different. Their term loops write disjoint sections of storage, but that storage and their FFTW plans are shared static variables. A second simultaneous entry could overwrite the first entry's arrays or rebuild its plans. The three-point module should borrow the ownership pattern, not call whole CFASTPT builders independently from many outer tasks. Prepare shared dependencies once, finish mutable cache construction, then let workers read them and write private outputs. `Pdelta` has a first-use run-mode latch, and `J_abl` explicitly prepares its gamma cache before its parallel loop. [Persistent scratch](../../../../../cfastpt/cfastpt.c); [gamma preparation](../../../../../cfastpt/cfastpt.c).

A cache example limits how literally that pattern should be copied. `J_abJ1J2Jk_ar` rebuilds for changes in size, term count, grid origin, or spacing. Its cached taper also depends on `c_window_width`, but that parameter is not included in the displayed rebuild condition. The existing fixed callers may retain one width; a proposed interface exposing taper variation cannot inherit that assumption. Its cache key must contain every configurable quantity used to fill the array, and a same-size taper-change test must demonstrate refresh. [Rebuild condition](../../../../../cfastpt/cfastpt.c); [taper construction](../../../../../cfastpt/cfastpt.c).

Runtime thread ownership matters beyond FFTs. The project exposes `set_omp_threads`, calls an OpenBLAS thread setter, and uses `ScopedSerialAlgebra` around dense algebra because the linked BLAS can also create workers. The current link includes `fftw3`, with no inspected call enabling internal FFTW threading. Outer OpenMP is therefore the existing pattern. Enabling internal FFT threads would require separate initialization, linking, and scheduling decisions. A future test should verify worker limits after importing other numerical libraries and after covariance operations. Thread setter (inspected host file `interface/interface.cpp`, line 442); [dense-algebra guard](../../../../../cosmolike/generic_interface.hpp).

## 5. Existing bindings reduce build work, but array ownership must be explicit

The project compiles C as GNU99, C++ as C++23, and links GSL, FFTW, Armadillo/OpenBLAS, and pybind11-related interfaces. Optimized compilation enables OpenMP and strict floating-point options. A first CPU module therefore needs source registration and bindings, not a new accelerator framework. The build produces a project-specific extension; adding a source file to the core directory alone does not add it to every project's binary. Build definitions (inspected host file `interface/MakefileCosmolike`, line 45); source lists and linking (inspected host file `interface/MakefileCosmolike`, line 174).

The array boundary needs shape, stride, lifetime, and ownership rules. Core multidimensional allocations include row-pointer tables and 64-byte row padding. A row of 100 doubles occupies 104 double slots; treating several rows as one tightly packed NumPy array would include padding and misplace subsequent rows. Return a packed array, or describe the physical strides and retain the owner for the view's lifetime. FFTW also needs compatible strides and alignment. Keep C complex arithmetic within the C boundary, since the existing non-Limber header deliberately excludes those declarations from C++ and specifies header ordering. Returning real and imaginary arrays avoids depending on an unverified C/C++ complex representation. [Allocation implementation](../../../../../cosmolike/basics.c); [complex boundary](../../../../../cosmolike/cosmo2D.h).

The first return value should remain an independent natural-component or aperture array, as proposed in Chapter 10. The current probe enumeration contains two-point statistics, not an aperture-third-moment entry. Extending the host's full data-vector layout needs explicit ordering, masks, and covariance dimensions. It can follow numerical agreement of the independent array interface. Source notices must also follow translated expressions: the core's MIT license does not replace fastnc, TreeCorr-derived, or other inherited notices; the integrator/Y6 license question recorded in Chapter 11 remains a distribution task.

## 6. Covariance reuse and the CPU integration question

**Confirmed:** the core covariance assemblers take measured field pairs and two-point kernels. Their connected contribution projects a matter trispectrum. These signatures do not supply the three-point covariance or its two-point cross-covariance. Reusing matrix loading, mask handling, and numerical integration infrastructure is possible; the required higher-order statistical expressions still need their own implementation or external covariance input. [Assembler interface](../../../../../cosmolike/covariances/assembly_cov.h).

There is also an existing state interaction to preserve during joint work. A covariance IA calculation calls `get_FPT_IA` and can replace Python-installed FAST-PT tables with C-generated tables. The origin flag then causes the data-vector path to require reinstallation rather than silently use a different table. A future workflow test must alternate mean, covariance, and mean calculations under both table providers. Giving the three-point module its own named storage avoids making that ownership problem larger. [Covariance call](../../../../../cosmolike/covariances/ia_cov.c); [origin enforcement](../../../../../cosmolike/pt_cfastpt.c).

CUDA is not a mathematical requirement for these integrals. The inspected CPU aperture-covariance implementation already calls `hcubature_v` for three- and six-dimensional integrals and `pcubature_v` for an eight-dimensional case. CosmoLike supplies fixed Gauss–Legendre rules and explicit tensor contractions; the inspected core sources and project link do not supply a Cuba or cubature integration interface. Repeatedly nesting its one-dimensional rule is possible mathematically, but $`n`$ nodes in each of $`d`$ dimensions require $`n^d`$ evaluations before reductions. The CPU design should first exploit symmetries, common power-spectrum reads, and batched evaluation, then choose fixed or adaptive multidimensional integration for the remaining expression. OpenMP across covariance entries or batches and SIMD within integrands are available without CUDA. Chapter 15 assesses the covariance formulas and their numerical scope. [CPU cubature calls](https://github.com/sheydenreich/threepoint/blob/08de9645a7294092995e5aeaf7b36e48e8fc10a3/classed_version/apertureStatisticsCovariance.cpp#L293); [core quadrature allocation](../../../../../cosmolike/basics.c).

The CPU reference already places OpenMP over the points supplied to its cubature callbacks. That provides a direct example of the desired interface: a batch of coordinates enters, and each worker fills a different output value. It does not prove that all nested dependencies are safe for concurrent initialization. The proposed port should install power, growth, halo, and FFT tables before entering these callbacks, then choose either parallel covariance entries or parallel point batches as its main worker layer. Its older `Cov_NonGaussian` entry returns only `T4_total`; it does not supply every term present in the CUDA version. A CPU port must track the requested term list explicitly. [Batched callback](https://github.com/sheydenreich/threepoint/blob/08de9645a7294092995e5aeaf7b36e48e8fc10a3/classed_version/apertureStatisticsCovariance.cpp#L407); [CPU non-Gaussian entry](https://github.com/sheydenreich/threepoint/blob/08de9645a7294092995e5aeaf7b36e48e8fc10a3/classed_version/apertureStatisticsCovariance.cpp#L61).

For an initial Fisher forecast with a fixed covariance, only the mean vector needs parameter derivatives. Varying the covariance later would introduce a second numerical requirement: changes between two nearby cosmologies must exceed the integration error. Independently adapted cubature partitions can produce noisy differences even when each matrix looks stable. Shared quadrature nodes where appropriate, recorded error estimates, and convergence of the resulting derivatives would then be acceptance tests. This is a future test requirement, not evidence that covariance derivatives are already reliable.

The next implementation decision should therefore use an explicit input and ownership specification: physical IA coefficients and priors, power/growth conventions, units and table coverage, serial setup boundaries, worker-owned arrays, and independent Y3/Y6 measurement definitions. Future numerical checks should establish each boundary before timing the optimized calculation. That sequence preserves the opportunities for substantial CPU acceleration while ensuring that agreement or disagreement can be traced to a specific scientific or numerical choice.
